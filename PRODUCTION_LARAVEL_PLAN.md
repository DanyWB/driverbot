# Production Laravel Plan

Дата: 2026-07-21.

## Контекст

Проект сейчас - Telegram-бот аренды байков на Node.js, grammy, PostgreSQL и Knex.
Бот уже содержит клиентский сценарий бронирования, базовую админку в Telegram, цены,
статусы, напоминания и данные по технике.

Новый вектор разработки: делать не MVP, а production-релиз системы, которая заменит
ручное ведение бронирований в Excel и станет основной операционной системой для аренды.

Заказчик выбрал вариант A: отдельный Laravel backend с web-админкой, при этом
Telegram-бот остается клиентским интерфейсом. Проект делается как первый
production-релиз, не как временный MVP.

## Главный архитектурный выбор

Целевая схема:

```text
Telegram Bot на Node.js
  -> Laravel API /api/v1/bot
  -> Laravel Services
  -> PostgreSQL

Laravel Web Admin: Vue 3 + TypeScript + Inertia
  -> Laravel Services
  -> PostgreSQL

Будущий клиентский сайт
  -> Laravel Public routes/API
  -> те же Laravel Services
  -> PostgreSQL
```

Laravel становится главным backend системы. В нем должна жить бизнес-логика:

- создание и изменение бронирований;
- проверка доступности техники;
- расчет, фиксация и ручная корректировка цены;
- смена дат;
- статусы бронирований;
- отмены, no-show, автоистечение заявок;
- документы и фото;
- уведомления;
- экспорт.

Node.js бот не переписывается полностью на первом этапе. Он остается отдельным
процессом и становится thin client: собирает ввод клиента, вызывает Laravel API и
показывает клиенту результат.

Laravel проектируется как backend всей rental-системы, а не только Telegram-бота.
Клиент хранится отдельно от Telegram identity, источник брони фиксируется как
`telegram`, `admin_*` или зарезервированный `website`. Полная архитектура закреплена
в `ARCHITECTURE.md`.

## Что остается в боте

Интерфейс для клиента должен остаться максимально похожим на текущий:

- выбор языка;
- регистрация/контактные данные;
- выбор категории/техники;
- выбор дат и времени;
- комментарий;
- подтверждение заявки;
- просмотр своих броней;
- отмена брони, если это разрешено правилами;
- загрузка документов, если включим этот сценарий.

Меняется не внешний сценарий, а внутренняя реализация. Бот больше не должен сам
решать, доступна ли техника, сколько стоит аренда и какой статус поставить. Эти
решения принимает Laravel.

## Что переносится в Laravel

В Laravel должны быть реализованы сервисы:

- `BookingService` - создание, подтверждение, изменение дат, отмена, no-show, завершение.
- `AvailabilityService` - проверка пересечений, блокирующие статусы, защита от двойных броней.
- `PricingService` - расчет цены, price snapshot, ручная корректировка итоговой цены.
- `VehicleService` - скутеры и машины, активность, фото, характеристики.
- `DocumentService` - документы клиента из бота и админки.
- `NotificationService` - уведомления админа и клиента через Telegram.
- `ExportService` - выгрузка бронирований в CSV.
- `AdminBookingService` - ручное создание брони из web-админки.

Смена техники внутри уже созданной брони в первый production-релиз не входит. Если
нужно заменить транспорт, админ отменяет старую заявку и создает новую.

## Web Admin

Админка должна заменить Excel как основной рабочий инструмент.

Технический стек админки: Vue 3, TypeScript и Inertia внутри Laravel. Admin routes
используют Laravel session/CSRF, а Inertia controllers вызывают общие application
actions напрямую. Отдельная SPA и отдельный REST API для собственной админки не нужны.

Основные разделы:

1. Бронирования
2. Timeline / шахматка занятости
3. Техника
4. Цены
5. Клиенты
6. Экспорт
7. Настройки/пользователи админки

### Таблица бронирований

Основной экран - таблица, похожая по смыслу на текущий Excel:

- ID/номер брони;
- дата начала;
- дата окончания;
- время выдачи, если указано;
- техника;
- тип техники: скутер/машина;
- клиент;
- телефон/Telegram;
- статус;
- итоговая цена;
- документы;
- комментарий;
- быстрые действия.

Нужны фильтры:

- по датам;
- по статусам;
- по технике;
- по типу транспорта;
- по клиенту;
- по активным/архивным броням.

Timeline обязателен в первом production-релизе. Он заменяет визуальную часть
текущего Excel: строки техники, дни по колонкам, цветные блоки броней по датам.
Цвета должны соответствовать статусам/категориям, а не храниться как произвольная
бизнес-логика.

Админ должен уметь создать бронь вручную из web-админки для клиента, который
позвонил или написал вне Telegram. Такая бронь должна сразу проверять доступность,
считать цену и блокировать технику.

### Карточка бронирования

В карточке заявки админ может:

- посмотреть все данные заявки;
- изменить даты аренды с повторной проверкой доступности;
- вручную скорректировать итоговую стоимость;
- подтвердить заявку;
- отменить заявку;
- отметить "клиент не приехал";
- завершить аренду;
- добавить внутренний комментарий;
- загрузить документы клиента вручную;
- посмотреть историю изменений.

Смена техники в карточке бронирования откладывается. Для первой версии выбран более
простой и надежный сценарий: отменить старую бронь и создать новую на другую технику.

### Техника

Система сразу проектируется под скутеры и машины.

Для каждой единицы техники:

- название;
- тип: scooter/bike/car;
- категория;
- код/номер;
- год;
- описание/характеристики;
- активна/неактивна;
- доступна/скрыта для бронирования;
- сортировка;
- несколько фото, ориентир - 3 фото на единицу.

Специфические характеристики машин и скутеров не разносятся по жестким полям в
первом production-релизе. Коробка, места, страховка, залог и похожие детали хранятся
в общем описании/характеристиках техники, чтобы не усложнять схему базы до появления
устойчивого формата данных.

### Цены

Цены должны редактироваться в админке без разработчика.

Правила:

- цена хранится в базе как итоговые суммы `1 day`, `7 days`, `14 days`, `21 days`, `month`;
- вся техника из Excel импортируется в БД, после чего ее можно включать/выключать;
- админ редактирует итоговые суммы, а backend рассчитывает дневные ставки;
- при создании брони цена фиксируется в самой заявке;
- будущие изменения прайса не меняют старые бронирования;
- при изменении дат Laravel автоматически пересчитывает цену;
- админ может вручную изменить итоговую стоимость перед подтверждением.
- `30+` дней используют месячный тариф;
- если аренда пересекает сезоны, расчет разбивается по дням;
- итог округляется до 100 бат.

Подробные правила описаны в `PRICING_IMPORT_SPEC.md`.

## Booking flow

Целевой поток:

1. Клиент в Telegram выбирает технику, даты и время.
2. Бот отправляет данные в Laravel API.
3. Laravel проверяет доступность и считает цену.
4. Laravel создает заявку.
5. Админ получает уведомление.
6. Админ проверяет заявку в web-админке.
7. Админ подтверждает, меняет цену/даты или отменяет.
8. После подтверждения клиент получает уведомление.
9. В день выдачи и за час до выдачи отправляются напоминания, если есть время.
10. После аренды админ завершает бронь или ставит no-show.

## Статусы

Предварительная production-модель:

- `process` - черновик клиента в боте, не должен бесконечно блокировать технику.
- `pending` - заявка отправлена администратору и ждет обработки.
- `approved` - бронь подтверждена админом.
- `active` - аренда фактически началась.
- `completed` - аренда завершена.
- `cancelled` - отменена админом.
- `cancelled_by_client` - отменена клиентом.
- `expired` - заявка истекла без обработки.
- `no_show` - клиент не приехал после подтверждения брони.

Блокирующие статусы для доступности техники:

- `pending`;
- `approved`;
- `active`.

Не блокируют технику:

- `process`;
- `cancelled`;
- `cancelled_by_client`;
- `expired`;
- `no_show`;
- `completed`.

Точное правило по `process` нужно подтвердить отдельно. Рекомендуемый вариант:
не блокировать технику черновиками или блокировать только на короткий TTL.

## Автоматизация

Нужно реализовать:

- уведомление админа о новой заявке;
- уведомление админа об отмене клиентом;
- уведомление клиента после approve;
- напоминание в день выдачи;
- напоминание за час до выдачи, если время указано;
- автоотмену pending-заявок, которые не обработаны за 24 часа;
- освобождение техники после отмены, expired и no-show.

Правила из финального ответа заказчика:

- если до начала аренды меньше 24 часов, клиент не отменяет бронь автоматически;
- кнопка отмены скрывается или показывает сообщение с просьбой написать менеджеру;
- автоматический запрос админу при такой поздней отмене не создается;
- при автоистечении pending-заявки клиент получает уведомление, почему бронь аннулирована;
- `no_show` доступен только для `approved`, потому что `active` означает, что аренда уже началась.

## Документы и депозит

Документы:

- заявка может уйти администратору без документов;
- клиент может загрузить документы позже через бот;
- админ может загрузить документы вручную в web-админке;
- документы не должны блокировать сам факт создания заявки, если заказчик не поменяет решение.

Файлы в первом production-релизе хранятся локально на сервере. S3/облачное хранилище
оставляется как будущий этап, если объем фото и документов начнет расти.

Депозит:

- пока не автоматизировать как полноценную финансовую систему;
- оставить возможность хранить заметку/факт по депозиту;
- отдельно уточнить: речь про бронировочный депозит или залог за технику.

## Оценка времени

Оценка дана с учетом работы через AI/Codex GPT-5.5 Extra High и уже существующей базы
Node.js-бота. Это не ручная оценка "с нуля", но и не быстрая MVP-задача.

Сумма этапов реализации: 112-144 часа.

Integration/review reserve: 12-20 часов.

Реалистичный итоговый коридор: 124-164 часа.

Для заказчика лучше закладывать: 130-165 часов.

Полная разбивка на 11 этапов, зависимости, риски и acceptance gates находится в
`IMPLEMENTATION_ROADMAP.md`. Его оценки являются актуальными при планировании.

Почему не меньше:

- Laravel становится новым центром системы, а не просто отдельной админкой.
- Бот нужно переподключить к API без поломки клиентского сценария.
- Нужна надежная модель статусов и доступности, чтобы не было двойных броней.
- Админка заменяет Excel, значит нужны фильтры, карточки, редактирование, экспорт.
- Production-релиз требует миграций, проверок, обработки ошибок, прав и тестирования.

## Нерекомендованные варианты

### Оставить бизнес-логику в Node.js, а Laravel сделать только админкой

Быстрее на старте, но плохо стратегически. Появятся две точки изменения данных:
бот и админка. Это повысит риск расхождения статусов, цен и доступности.

### Полностью переписать Telegram-бота на Laravel сразу

Архитектурно возможно, но это увеличит сроки и риски. Текущий бот уже работает, а
его внешний сценарий в основном сохраняется. На первом этапе выгоднее оставить Node.js
бот как клиент Laravel API.

Оценка такого полного переписывания: 170-240 часов.

## Открытые вопросы

Перед финальной спецификацией нужно подтвердить:

- реальный Telegram username менеджера для сообщения поздней отмены;
- нужен ли отдельный статус "готово к выдаче" между `approved` и `active`;
- точную production-конфигурацию сервера после локальной разработки.
