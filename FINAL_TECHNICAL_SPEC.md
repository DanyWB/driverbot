# Финальное ТЗ: Laravel backend, web-админка и Telegram-бот

Дата: 2026-07-21.

## 1. Цель проекта

Сделать первый production-релиз системы управления арендой транспорта для Drive
Phangan.

Система должна заменить ручное ведение бронирований в Excel и стать единым центром
для:

- бронирований;
- техники: скутеры и машины;
- цен;
- фото;
- документов;
- статусов;
- уведомлений;
- экспорта данных.

Telegram-бот остается клиентским интерфейсом. Web-админка становится рабочим
интерфейсом заказчика и менеджеров. Laravel становится главным backend, где живет
бизнес-логика.

## 2. Целевая архитектура

```text
Клиент
  -> Telegram Bot на Node.js
  -> Laravel Bot API
  -> Laravel Services
  -> PostgreSQL

Администратор
  -> Laravel Web Admin
  -> Laravel Services
  -> PostgreSQL

Laravel Scheduler / Queue
  -> автоотмена, уведомления, напоминания
  -> Telegram Bot API

Будущий клиентский сайт
  -> Laravel public routes или /api/v1/public
  -> те же Laravel Services
  -> PostgreSQL
```

### 2.1. Почему так

Текущий бот уже работает и содержит клиентский сценарий. Полная перепись бота на
Laravel сразу увеличит сроки и риск регрессий.

Правильная граница ответственности:

- Node.js бот отвечает за Telegram UI и шаги диалога.
- Laravel отвечает за бизнес-логику и данные.
- Web-админка на Vue 3 + TypeScript + Inertia работает с теми же Laravel-сервисами,
  что и бот.
- Клиент не зависит от Telegram: внешние identities и контакты привязываются к общей
  сущности Customer.
- Будущий сайт вызывает те же booking, availability и pricing use cases.

Так не будет двух разных реализаций бронирования: одна для бота, другая для админки.

## 3. Что остается в Telegram-боте

Внешний интерфейс бота для клиента должен остаться максимально похожим на текущий.

Остается:

- выбор языка;
- регистрация или уточнение данных клиента;
- выбор типа транспорта;
- выбор категории;
- выбор конкретной техники;
- выбор дат;
- выбор времени, если используется;
- добавление комментария;
- подтверждение заявки;
- просмотр своих бронирований;
- отмена брони по правилам;
- загрузка документов, если клиент делает это через бот;
- получение уведомлений и напоминаний.

Меняется внутренняя реализация:

- бот не считает цену сам;
- бот не решает сам, доступна ли техника;
- бот не выставляет финальные статусы сам;
- бот не должен напрямую менять ключевые бизнес-таблицы в обход Laravel;
- бот вызывает Laravel API и показывает клиенту ответ.

## 4. Что переносится в Laravel

Laravel становится главным backend.

Обязательные сервисы:

- `BookingService` - создание, изменение дат, подтверждение, отмена, no-show, старт и завершение аренды.
- `AvailabilityService` - проверка занятости техники и защита от двойных броней.
- `PricingService` - расчет цены, фиксация price snapshot, ручная корректировка.
- `VehicleService` - скутеры, машины, фото, активность, отображение.
- `DocumentService` - загрузка и хранение документов.
- `NotificationService` - сообщения клиенту и админу через Telegram.
- `ExportService` - CSV-выгрузка.
- `AdminAuditService` - история действий админа.

## 5. Границы первого production-релиза

Входит:

- Laravel backend;
- web-админка;
- API для Telegram-бота;
- адаптация текущего Node.js бота под Laravel API;
- единая логика бронирований;
- ручное создание брони из web-админки;
- timeline/шахматка занятости по технике и датам;
- редактирование дат в админке;
- автоматический перерасчет цены при изменении дат;
- ручная корректировка итоговой цены;
- скутеры и машины в одной системе;
- фото техники;
- документы клиента;
- CSV-экспорт;
- автоотмена pending-заявок через 24 часа;
- уведомления клиенту и админу;
- статус no-show;
- локальное хранение файлов на сервере;
- базовая авторизация админки;
- production-подготовка: env, scheduler, queue/supervisor, проверки.

Не входит в первый production-релиз:

- смена техники внутри существующей брони;
- полноценная финансовая система депозитов/залогов;
- онлайн-оплата;
- облачное хранилище S3;
- XLSX-экспорт;
- отдельный публичный сайт для клиентов;
- сложные роли и права уровня CRM;
- жесткие отдельные поля для всех характеристик машин.
- автоматический импорт старых броней из Excel как боевых данных.

При этом архитектурная готовность к публичному сайту входит: channel-independent
Customer, источник `website`, reusable use cases, публично пригодный каталог и
зарезервированный versioned API.

## 6. Сущности и данные

### 6.1. Customers / Contacts / Identities

Клиент не должен определяться через Telegram ID.

`customers`:

- ID;
- имя;
- язык;
- внутренняя заметка;
- дата создания;
- дата обновления.

`customer_contacts`:

- customer_id;
- type: `phone`, `email`, `whatsapp`, `telegram_username`;
- value и normalized_value;
- is_primary;
- verified_at, если применимо.

`customer_identities`:

- customer_id;
- provider: `telegram`, `web`;
- external_id;
- metadata;
- уникальная пара provider/external_id.

Такая схема позволяет одному клиенту бронировать через Telegram, администратора и
будущий сайт без создания трех несвязанных профилей.

Админ:

- email/логин;
- пароль;
- имя;
- роль/тип доступа, на первом релизе один полный админ;
- активен/неактивен;
- дата последнего входа.

На первом production-релизе делаем один тип администратора с полным доступом. Сложные
роли можно добавить позже, если появятся несколько операторов с разными правами.

### 6.2. Vehicles

Доменная сущность и новая таблица называются `Vehicle` / `vehicles`. Старую таблицу
`bikes` Laravel не использует после cutover.

Поля:

- ID;
- type: `bike`, `scooter`, `car`;
- category_id;
- name;
- inventory_code;
- year;
- description;
- characteristics_text;
- emoji или короткая метка, если используется в боте;
- is_active;
- is_visible_for_booking;
- sort_order;
- pricing_profile;
- created_at;
- updated_at.

Решение по машинам:

- не делать отдельные жесткие поля `gearbox`, `seats`, `insurance`, `deposit`;
- хранить различающиеся характеристики текстом в `characteristics_text`;
- позже можно нормализовать, если появится устойчивый формат данных.

### 6.3. Vehicle Photos

Фото техники:

- ID;
- vehicle_id;
- file_path;
- public_url или storage reference;
- sort_order;
- is_primary;
- created_at.

Ориентир: 3 фото на единицу техники.

Фото техники можно показывать в админке и в Telegram-боте.

### 6.4. Prices

Цены хранятся в базе и редактируются через админку.

Минимальные поля:

- vehicle_id;
- season_key: `high`, `middle`, `low`;
- tier_key: `1d`, `7d`, `14d`, `21d`, `month`;
- min_days;
- max_days;
- anchor_days;
- package_total;
- daily_rate, вычисляется из `package_total / anchor_days`;
- currency;
- is_active;
- created_at;
- updated_at.

Правило:

- админ редактирует итоговые суммы тарифов;
- дневные ставки и цена бронирования рассчитываются автоматически на backend;
- при создании брони цена фиксируется в заявке;
- изменение прайса в будущем не меняет старые брони;
- админ может вручную исправить итоговую цену.

### 6.5. Bookings / Rentals

Основная сущность бронирования:

- ID;
- public_id;
- customer_id;
- vehicle_id;
- start_date;
- end_date;
- start_time, если указано;
- end_time, если нужно;
- status;
- source: `telegram`, `admin_phone`, `admin_whatsapp`, `admin_instagram`,
  `admin_manual`, `website`;
- client_comment;
- admin_note;
- cancellation_reason;
- no_show_reason, опционально;
- created_at;
- updated_at;
- confirmed_at;
- approved_at;
- activated_at;
- completed_at;
- cancelled_at;
- expired_at;
- no_show_at.

Новая таблица называется `bookings`. Старая `rentals` остается только в legacy-базе
до завершения cutover и не является частью новой доменной модели.

### 6.6. Price Snapshot

В брони нужно хранить снимок цены:

- calculated_days;
- tier_key;
- calculated_total;
- rounded_total;
- manual_total;
- final_total;
- currency;
- breakdown_json;
- pricing_source;
- price_overridden_by_admin_id;
- price_override_reason;
- price_calculated_at.

Это защищает старые бронирования от изменений прайса.

### 6.7. Documents

Документы клиента:

- ID;
- booking_id, если документ относится к конкретной брони;
- customer_id;
- type: passport/photo/other;
- file_path;
- original_filename;
- uploaded_by: `client`, `admin`;
- uploaded_by_admin_id, если загрузил админ;
- created_at.

Документы не обязательны для создания заявки, если заказчик не поменяет решение.

### 6.8. Audit Log

Нужно логировать важные действия:

- кто подтвердил бронь;
- кто отменил бронь;
- кто изменил даты;
- кто изменил цену;
- кто загрузил документ;
- кто отметил no-show;
- старое значение;
- новое значение;
- дата действия.

Это важно, потому что админка заменяет Excel и станет операционной системой бизнеса.

## 7. Статусы бронирования

### 7.1. Статусы

- `process` - черновик клиента в боте.
- `pending` - заявка отправлена и ждет решения админа.
- `approved` - бронь подтверждена админом.
- `active` - клиент забрал транспорт, аренда началась.
- `completed` - аренда завершена.
- `cancelled` - отменена админом.
- `cancelled_by_client` - отменена клиентом.
- `expired` - pending-заявка не обработана за 24 часа.
- `no_show` - клиент не приехал по подтвержденной брони.

### 7.2. Блокировка техники

Блокируют технику:

- `pending`;
- `approved`;
- `active`.

Не блокируют технику:

- `process`;
- `completed`;
- `cancelled`;
- `cancelled_by_client`;
- `expired`;
- `no_show`.

Решение для первого production-релиза: `process` не блокирует технику. Доступность
повторно проверяется перед созданием `pending`-заявки.

### 7.3. Переходы статусов

```text
process -> pending
process -> cancelled_by_client

pending -> approved
pending -> cancelled
pending -> cancelled_by_client
pending -> expired

approved -> active
approved -> cancelled
approved -> cancelled_by_client, если до начала >= 24 часа
approved -> no_show

active -> completed
active -> cancelled, только админский аварийный сценарий
```

Запрещено:

- `active -> no_show`;
- `completed -> no_show`;
- `cancelled -> approved` без создания новой брони;
- менять технику внутри брони в первом production-релизе.

## 8. Правила отмены

### 8.1. Отмена клиентом

До подтверждения:

- клиент может отменить свою pending-заявку через бот;
- статус становится `cancelled_by_client`;
- техника освобождается.

После подтверждения:

- если до начала аренды 24 часа или больше, клиент может отменить бронь через бот;
- статус становится `cancelled_by_client`;
- админ получает уведомление;
- техника освобождается.

Менее чем за 24 часа:

- автоматическая отмена через бот запрещена;
- кнопку лучше скрыть или заменить действие кнопки;
- если клиент нажимает отмену, бот показывает сообщение:

```text
До начала аренды осталось менее 24 часов. Для отмены бронирования и уточнения деталей по предоплате, пожалуйста, свяжитесь с менеджером напрямую: @username
```

- автоматический запрос админу не создается;
- клиент должен написать менеджеру лично.

Нужно заменить `@username` на реальный Telegram-контакт менеджера.

### 8.2. Отмена админом

Админ может отменить:

- pending;
- approved;
- active только в исключительном ручном сценарии.

При отмене админом:

- статус становится `cancelled`;
- техника освобождается, если бронь блокировала технику;
- клиент получает уведомление, если включено уведомление для такого действия;
- действие пишется в audit log.

## 9. Auto-expire pending-заявок

Если заявка в статусе `pending` не обработана за 24 часа:

- Laravel scheduler переводит ее в `expired`;
- техника освобождается;
- клиент получает сообщение:

```text
К сожалению, ваш запрос на бронирование не был подтвержден вовремя. Техника была освобождена. Вы можете создать новую заявку или связаться с нами для уточнения деталей
```

Технически:

- scheduler запускается регулярно, например каждые 5-15 минут;
- обработка должна быть идемпотентной;
- нельзя повторно отправлять одно и то же уведомление;
- нужно логировать дату `expired_at`.

## 10. No-show

No-show используется только для `approved`.

Правило:

- `approved` означает, что бронь подтверждена, но клиент еще не забрал транспорт;
- `active` означает, что клиент уже пользуется транспортом;
- если статус уже `active`, это не может быть no-show.

Действие админа:

- открыть карточку брони;
- нажать "Клиент не приехал";
- подтвердить действие;
- статус становится `no_show`;
- техника освобождается;
- действие пишется в audit log.

Кнопку no-show желательно показывать только:

- для `approved`;
- в день старта или после даты/времени старта.

## 11. Изменение дат

Админ может изменить даты аренды в карточке бронирования.

При изменении дат Laravel должен:

1. Проверить, что бронь находится в разрешенном статусе.
2. Проверить доступность текущей техники на новые даты.
3. Исключить текущую бронь из проверки пересечений.
4. Автоматически пересчитать цену.
5. Показать админу старую цену и новую расчетную цену.
6. Дать админу возможность оставить расчетную цену или вручную исправить итоговую.
7. Сохранить изменения.
8. Записать действие в audit log.
9. Отправить клиенту уведомление об изменении дат и/или цены, если у клиента есть
   Telegram-канал связи.

Смена техники при изменении дат не делается. Если нужна другая техника, создается
новая бронь.

## 12. Расчет цены

Правило первого production-релиза:

- цены хранятся в базе как итоговые суммы за `1 day`, `7 days`, `14 days`, `21 days`, `month`;
- админ редактирует именно итоговые суммы, а не скрытые коэффициенты;
- Laravel автоматически рассчитывает дневные ставки из итоговых сумм;
- при создании заявки фиксируется price snapshot;
- при изменении дат цена пересчитывается;
- админ может вручную скорректировать итоговую цену.

Подтвержденная формула:

- количество дней считается по календарным дням включительно;
- тарифный уровень выбирается по общей длительности аренды;
- `1-6` дней -> тариф `1 day`;
- `7-13` дней -> тариф `7 days`;
- `14-20` дней -> тариф `14 days`;
- `21-29` дней -> тариф `21 days`;
- `30+` дней -> месячный тариф `month`;
- если аренда пересекает разные сезоны, расчет разбивается по дням;
- для каждого дня берется сезон этого дня и дневная ставка выбранного тарифного уровня;
- итоговая цена округляется до 100 бат.

Пример:

- клиент берет транспорт на 30 дней;
- 15 дней попадают в high season, 15 дней в middle season;
- общий срок `30+`, значит используется месячный тариф;
- 15 дней считаются по дневной ставке месячного тарифа high season;
- 15 дней считаются по дневной ставке месячного тарифа middle season;
- суммы складываются и округляются до 100 бат.

Это правило должно жить в Laravel `PricingService`. Telegram-бот и web-админка не
должны дублировать формулу.

## 13. Смена техники

Смена техники внутри существующей брони в первый production-релиз не входит.

Выбранный процесс:

1. Админ отменяет старую бронь.
2. Админ или клиент создает новую бронь на другую технику.
3. Система заново проверяет доступность и считает цену.

Причина:

- меньше риск сломать доступность;
- меньше сложность статусов;
- меньше объем разработки;
- подходит под текущий бизнес-процесс.

## 14. Web-админка

### 14.1. Авторизация

Нужна закрытая админка.

Минимально:

Желательно:

- возможность отключить админа.

### 14.2. Бронирования: список

Главный рабочий экран.

Колонки:

- public ID;
- статус;
- дата начала;
- дата окончания;
- время выдачи;
- техника;
- тип техники;
- клиент;
- телефон;
- Telegram username;
- расчетная цена;
- итоговая цена;
- документы: есть/нет;
- комментарий;
- дата создания;
- быстрые действия.

Фильтры:

- период;
- статус;
- тип транспорта;
- техника;
- клиент/телефон;
- только активные;
- архивные;

Сортировка:

Действия из списка:

### 14.3. Бронирования: timeline / шахматка

Timeline обязателен в первом production-релизе, потому что он заменяет текущий
Excel-лист занятости.

Назначение:

- быстро видеть занятость техники по датам;
- проверять свободные окна;
- работать с клиентами, которые пишут или звонят не через Telegram;
- открывать бронь кликом по блоку.

Вид:

- строки: техника;
- колонки: дни выбранного периода;
- блок на строке техники: бронь;
- цвет блока: визуальная категория/статус брони;
- клик по блоку: карточка брони;
- клик по свободному периоду или кнопка "Создать бронь": форма ручного создания.

Фильтры:

- месяц/период;
- тип транспорта;
- категория;
- конкретная техника;
- статус;
- активная/скрытая техника.

Цвета:

- цвета из Excel нужно перевести в понятные категории, а не хранить как произвольные
  цвета;
- базовый маппинг: свободно, pending, approved, active, completed, cancelled,
  no-show, служебная блокировка/ремонт;
- палитру выбираем сами по статусам: neutral для свободно/архивно, yellow/orange
  для ожидания, green для подтвержденной/активной аренды, red для отмен/no-show,
  gray/blue для служебной блокировки.

Ограничение первого релиза:

- drag-and-drop перенос броней не обязателен;
- изменение дат выполняется через карточку брони, чтобы Laravel проверял доступность
  и пересчитывал цену.

### 14.4. Ручное создание брони из админки

Ручное создание обязательно входит в первый production-релиз.

Сценарий:

1. Клиент звонит или пишет не через Telegram.
2. Админ открывает timeline и смотрит доступность.
3. Админ выбирает свободную технику и даты.
4. Laravel проверяет доступность.
5. Laravel автоматически считает цену.
6. Админ вводит данные клиента.
7. Админ может вручную скорректировать финальную цену.
8. Бронь создается сразу из админки.

Форма ручной брони:

- клиент: выбрать существующего или создать нового;
- имя клиента;
- телефон;
- Telegram username, если есть;
- техника;
- дата начала;
- дата окончания;
- время выдачи, если есть;
- комментарий клиента/источник заявки;
- внутренний комментарий админа;
- payment/deposit note, если используем;
- расчетная цена;
- финальная цена.

Рекомендуемый статус:

- если админ сразу договорился с клиентом, бронь создается как `approved`;
- если заявка требует уточнения, бронь можно создать как `pending`.

### 14.5. Бронирования: карточка

Карточка должна показывать:

- номер брони;
- статус;
- клиента;
- контактные данные;
- технику;
- даты;
- время;
- цену;
- комментарий клиента;
- внутренний комментарий админа;
- документы;
- историю действий.

Действия:

- подтвердить pending;
- изменить даты;
- пересчитать цену;
- вручную изменить итоговую цену;
- отменить;
- отметить no-show;
- перевести в active;
- завершить active;
- загрузить документ;
- добавить заметку.

Ограничения:

- no-show только для approved;
- active нельзя перевести в no-show;
- технику в карточке не меняем;
- поздняя клиентская отмена через бот не выполняется автоматически.

### 14.6. Техника

Раздел нужен для управления скутерами и машинами.

Действия:

- добавить технику;
- редактировать технику;
- отключить технику;
- скрыть из бронирования;
- загрузить фото;
- выбрать главное фото;
- изменить сортировку;
- указать общий текст характеристик.

Поля формы:

- название;
- тип;
- категория;
- инвентарный код;
- год;
- описание;
- характеристики текстом;
- pricing profile;
- активность;
- видимость в боте;
- сортировка.

### 14.7. Цены

Раздел нужен, чтобы заказчик мог сам менять цены.

Функции:

- посмотреть цены по технике/профилю;
- редактировать тарифы;
- включать/выключать тариф;
- видеть дату последнего изменения;
- проверять, что активная техника имеет нужные цены.

Важно:

- изменение цены не должно менять старые брони;
- старые брони используют сохраненный price snapshot.

### 14.8. Клиенты

Минимальный раздел:

- список клиентов;
- поиск по имени, телефону, Telegram;
- карточка клиента;
- история бронирований;
- документы клиента.

### 14.9. CSV-экспорт

Экспорт должен работать из списка бронирований с учетом фильтров.

Формат:

- CSV;
- кодировка UTF-8, желательно с BOM для корректного открытия в Excel;
- разделитель уточнить: запятая или точка с запятой.

Базовые колонки:

- booking_public_id;
- status;
- vehicle_name;
- vehicle_type;
- start_date;
- end_date;
- start_time;
- client_name;
- client_phone;
- telegram_username;
- final_total;
- currency;
- client_comment;
- admin_note;
- created_at.

Состав CSV основан на уже разобранном Excel и списке полей этого раздела. Дополнительные
колонки можно добавить как приемочную правку без изменения архитектуры.

## 15. API между ботом и Laravel

Контракт фиксируется в OpenAPI и версионируется. Базовый путь bot API:
`/api/v1/bot`.

### 15.1. Auth

Бот ходит в Laravel API по серверному API token.

Требования:

- токен хранится в `.env` бота;
- Laravel проверяет токен на bot API routes;
- API routes недоступны публично без токена;
- обязательны rate limit, HTTPS и возможность ротации токена.

### 15.2. Основные endpoints

Vehicles:

```text
GET /api/v1/bot/vehicles
GET /api/v1/bot/vehicles/available?type=&category_id=&start_date=&end_date=
GET /api/v1/bot/vehicles/{id}
```

Pricing:

```text
POST /api/v1/bot/quotes
```

Bookings:

```text
POST /api/v1/bot/bookings
GET /api/v1/bot/customers/me/bookings
GET /api/v1/bot/bookings/{public_id}
POST /api/v1/bot/bookings/{public_id}/cancel
POST /api/v1/bot/bookings/{public_id}/documents
```

Customers:

```text
POST /api/v1/bot/customers/sync
PATCH /api/v1/bot/customers/me
```

Все mutation endpoints принимают `Idempotency-Key`. Повтор Telegram update или
сетевой retry не должен создавать повторную бронь либо повторять статусный переход.

### 15.3. Поведение API

Laravel API должен возвращать боту не только данные, но и понятный результат действия:

- success;
- business error;
- validation error;
- unavailable;
- late cancellation forbidden;
- price changed;
- booking expired.

Бот должен показывать клиенту готовое понятное сообщение или строить его из
стабильных кодов ответа.

## 16. Уведомления

### 16.1. Админу

Админ получает уведомление:

- новая pending-заявка;
- клиент отменил бронь, если отмена разрешена;
- системная ошибка отправки уведомления, если нужен alert.

Поздняя отмена менее чем за 24 часа:

- автоматический запрос админу не создается;
- бот просит клиента написать менеджеру напрямую.

### 16.2. Клиенту

Клиент получает уведомление:

- заявка создана и ожидает подтверждения;
- заявка подтверждена;
- заявка отменена админом;
- заявка истекла через 24 часа без подтверждения;
- напоминание в день выдачи;
- напоминание за час до выдачи, если время указано.

## 17. Файлы

Решение первого production-релиза: локальное хранение на сервере.

Фото техники:

- публичные или semi-public;
- можно отдавать в боте и админке.

Документы клиента:

- приватные;
- доступны только администраторам;
- не должны лежать в публичной директории без защиты;
- нужна проверка типа и размера файла.

S3 не делаем в первом релизе, но Laravel Storage нужно использовать так, чтобы
позже можно было переключить диск хранения.

## 18. Надежность и нагрузка

Основной риск под нагрузкой - двойная бронь одной техники на пересекающиеся даты.

Нужно:

- все операции создания/подтверждения/изменения дат делать через Laravel services;
- использовать DB transaction;
- повторно проверять доступность перед записью;
- проверять пересечения только по блокирующим статусам;
- исключать текущую бронь при изменении дат;
- добавить индексы по `vehicle_id`, `status`, `start_date`, `end_date`;
- добавить обязательную DB-level защиту от пересечений blocking intervals.

Принятое решение:

- единая таблица `vehicle_occupancies` для броней и maintenance;
- transaction + `FOR UPDATE` для строки техники;
- PostgreSQL exclusion constraint по vehicle/date range;
- concurrency test с двумя параллельными запросами;
- конфликт возвращается как `409 VEHICLE_UNAVAILABLE`.

## 19. Миграция с текущего проекта

Текущий проект уже имеет:

- `users`;
- `bikes`;
- `bike_prices`;
- `rentals`;
- `reminders`;
- статусы;
- часть admin fields;
- `vehicle_type` в `bikes`.

Принятый путь:

1. Создать новую Laravel-схему миграциями с нормальными доменными именами.
2. Не переносить старые брони и тестовые черновики как production-данные.
3. Импортировать финальную технику и цены повторяемой command с dry-run.
4. Проверить количество техники, полноту тарифов и контрольные расчеты.
5. Перевести бизнес-операции Node.js-бота на Laravel API под feature flag.
6. В момент cutover убрать у бота DB credentials и полностью запретить dual-write.
7. Старую базу оставить read-only на согласованный период для проверки/отката.

## 20. Тестирование

Обязательные проверки:

- создание заявки из бота;
- отсутствие двойной брони при одинаковых датах;
- pending блокирует технику;
- approved блокирует технику;
- active блокирует технику;
- cancelled/expired/no_show/completed не блокируют технику;
- автоистечение pending через 24 часа;
- уведомление клиента при expired;
- отмена клиентом за 24+ часа;
- запрет отмены клиентом менее чем за 24 часа;
- no-show доступен только для approved;
- изменение дат пересчитывает цену;
- ручная цена сохраняется;
- изменение прайса не меняет старую бронь;
- CSV открывается в Excel/Google Sheets;
- документы не публичны без доступа;
- бот корректно обрабатывает ошибки Laravel API.

## 21. Acceptance Criteria

Задача считается готовой, когда:

- заказчик может открыть web-админку и видеть таблицу бронирований;
- заявка из Telegram появляется в админке;
- админ может подтвердить или отменить заявку;
- админ может изменить даты и увидеть пересчитанную цену;
- админ может вручную исправить итоговую цену;
- техника корректно блокируется на занятые даты;
- клиент не может автоматически отменить approved-бронь менее чем за 24 часа;
- pending-заявка истекает через 24 часа с уведомлением клиента;
- no-show работает только для approved;
- админ может управлять скутерами и машинами;
- админ может добавить фото техники;
- админ может редактировать цены;
- можно выгрузить бронирования в CSV;
- бот продолжает работать как клиентский интерфейс;
- бизнес-логика бронирования находится в Laravel, а не дублируется в боте;
- production окружение настроено и задокументировано.
